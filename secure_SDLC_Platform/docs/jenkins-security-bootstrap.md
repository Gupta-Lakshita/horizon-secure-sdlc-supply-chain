# Jenkins Security Bootstrap

## Purpose

Client-hosted Horizon installs must not run Jenkins in anonymous/open mode. The platform chart now enables Jenkins local security during startup and creates two runtime identities from a Kubernetes Secret:

- `JENKINS_ADMIN_USER`: human/operator break-glass administrator.
- `JENKINS_SERVICE_USER`: backend service account used by Horizon backend to create and trigger Jenkins jobs.

Passwords and API tokens are generated by Helm/Kubernetes on first install and preserved across upgrades. They should not be committed to `client-values.yaml`.

## Runtime Secret

Default Secret:

```text
horizon-jenkins-credentials
```

Default Namespace:

```text
<installer.namespace>
```

Default keys:

```text
JENKINS_ADMIN_USER
JENKINS_ADMIN_PASSWORD
JENKINS_SERVICE_USER
JENKINS_SERVICE_PASSWORD
JENKINS_SERVICE_TOKEN
```

The backend reads `JENKINS_SERVICE_USER` and `JENKINS_SERVICE_TOKEN` from this Secret. This removes the need to manually create a Jenkins API token through the UI during initial onboarding.

## Helm Values

```yaml
components:
  jenkins:
    enabled: true
    image: 426946630837.dkr.ecr.us-east-1.amazonaws.com/horizon/jenkins:1.0.8
    securityEnabled: true
    credentialsSecretName: horizon-jenkins-credentials
    adminUser: horizon-admin
    serviceUser: horizon-backend
```

Do not put `adminPassword`, `servicePassword`, or `apiToken` in Git for enterprise customers. Use generated values, External Secrets, or AWS Secrets Manager.

## Apply The Fix

Run the platform phase again:

```bash
bash secure_SDLC_Platform/scripts/install.sh \
  --phase platform \
  --environment DEV \
  -f secure_SDLC_Platform/examples/oracle-hybrid-onboarding-values.yaml \
  --auto-approve
```

Then restart Jenkins and backend if Helm does not roll them automatically:

```bash
kubectl rollout restart deploy/horizon-jenkins -n oracle-horizon-platform
kubectl rollout restart deploy/horizon-backend -n oracle-horizon-platform
kubectl rollout status deploy/horizon-jenkins -n oracle-horizon-platform
kubectl rollout status deploy/horizon-backend -n oracle-horizon-platform
```

## Retrieve Jenkins Admin Login

```bash
kubectl get secret horizon-jenkins-credentials \
  -n oracle-horizon-platform \
  -o jsonpath='{.data.JENKINS_ADMIN_USER}' | base64 -d
echo

kubectl get secret horizon-jenkins-credentials \
  -n oracle-horizon-platform \
  -o jsonpath='{.data.JENKINS_ADMIN_PASSWORD}' | base64 -d
echo
```

Open Jenkins and log in using those values.

## Verify Backend API Token

Do not print the token in normal operations. Only verify that it exists:

```bash
kubectl exec deploy/horizon-backend \
  -n oracle-horizon-platform \
  -- sh -c 'test -n "$JENKINS_TOKEN" && echo jenkins_token_present'
```

Then open the pipeline UI. The environment preflight should no longer show:

```text
Backend is missing a real Jenkins API token.
```

## Enterprise Notes

- For regulated clients, replace the generated Kubernetes Secret with External Secrets backed by AWS Secrets Manager.
- The Jenkins service token is client-owned and must be rotated during incident response or client offboarding.
- The Horizon backend should use only the service identity, not a human Jenkins admin identity, for job creation and triggering.
